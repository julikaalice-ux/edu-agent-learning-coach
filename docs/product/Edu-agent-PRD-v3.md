## 一页概览

**是什么**：一个学习教练 agent。它和通用聊天机器人的区别是：不只回答学习者问出来的问题，还会主动用小题检查是不是真的学会了；答错时先找原因再讲；学完后把学到的东西整理成笔记，下次接着用。

**三个产品判断**

1. “学会”以学习者独立答对为准，不以“我懂了”为准。
2. 错误是最有价值的学习材料，要找到原因再讲。
3. 学到的东西要沉淀下来，但要学习者同意才保存。

**技术上的核心做法**

- **一个主 agent 调度四个子 agent**（核对、画图、出题、笔记）。要查资料时，主 agent 自己写搜索词，程序去搜。主 agent 每轮决定派哪几个子 agent、谁要等谁；没有依赖的子 agent 同时开工。子 agent 之间不直接对话，结果都交回主 agent（结构图见 4.1，并行方式见 4.2）。
- **模型提出，程序决定**：模型负责理解和生成；判分、权限、执行顺序、写入数据这些必须确定的事，由程序做。

**当前状态**

- 主流程可以运行。模型部署在 Azure AI Foundry，演示网页部署在 Hugging Face。
- 共 321 个自动测试，其中 26 个需要完整的框架环境才能运行。
- 主要缺口见第六部分。

## 一、为什么做

### 1.1 现有工具的问题

- **通用 AI 聊天工具**能答疑，但默认用户知道自己哪里不懂。它回答你问的问题，不回答你没问出来的问题。
- **错题本和刷题 App** 记录了错误，但不解释错误为什么发生，同样的错反复犯。
- **网课和讲解视频**以看为主，学习停在“看懂了”的错觉里，记得不牢。
- **笔记工具**只负责存，不负责整理，记下的知识点零散，彼此没有关联。

### 1.2 背后的原因：学习科学的三个发现

这些问题不只是缺少某个工具，而是人学习时本来就有的弱点。AI 的机会在于补上这些弱点。

**发现一：人会系统性地高估自己的理解。** 人们普遍觉得自己懂了，被要求“解释一下它是怎么工作的”时，才发现其实不懂。因果链越长的知识，这种错觉越严重（Rozenblit & Keil, 2002）。学生对自己掌握程度的判断也普遍偏高（Hacker et al., 2013）。

**发现二：错误被浪费了。** 传统学习把错误当成要避免的事。元分析显示，鼓励犯错并要求学习者分析错误原因的训练，迁移到新任务的效果明显更好（效应量 d≈0.80，Keith & Frese, 2008）；“先尝试、再讲解”也优于“先讲解、再练习”（Kapur, 2014）。起作用的是分析原因和反思，不是犯错本身。

**发现三：学习停在被动层，知识不成结构。** 投入越主动，学习效果越好，从被动、主动、建构到互动四个层次依次提高（Chi & Wylie, 2014）；图文结合优于纯文字（Mayer, 2002）；做笔记、画概念图是被反复验证过的有效学习活动（Kobayashi, 2005；Wang et al., 2025）。

### 1.3 推导：从发现到产品原则

| 发现 | AI 能做什么 | 推导出的产品原则 | 对应机制 |
|---|---|---|---|
| 人高估自己的理解，而且察觉不到 | 主动出题、追问“用你的话说一遍”，成本很低 | “学会”以独立答对为准，不等用户提问就去检查 | 机制一：模糊地带探测 |
| 错误被浪费 | 对每次答错分析原因，换一种讲法 | 答错先找原因，再针对原因讲 | 机制二：错误归因 |
| 学习被动、知识零散 | 生成可操作的图；把对话整理成结构化笔记 | 让学习者动手；学到的东西要沉淀 | 机制三：多模态讲解；机制四：结构化沉淀 |

除了上面三条“要做什么”，还有三个风险推导出“不能怎么做”：

| 风险 | 推导出的原则 | 落在哪里 |
|---|---|---|
| 探测用过了头就变成打扰：学习者不想学时还在出题追问 | 只在学习者想学的时候探测 | 机制五：学习意愿边界 |
| 模型会编造，也会高估自己的判断 | 模型提出，程序决定：事实要查证，判分由程序做，链接只能来自真实检索结果 | 第四部分 4.5 |
| 用户多数是未成年人 | 学习记录默认不存，问过才存；可能未满 14 岁时要家长同意；不记个人信息，不记情绪 | 第三部分 3.1、3.4 |

### 1.4 目标与用户

**产品目标**：做一位“知道你可能哪里没懂”的学习教练，而不是“有问必答”的搜索引擎。

**用户**：以 K12 学生为主，同时支持学龄前儿童（由家长陪着用）、大学生和在职学习者。第一次使用时程序会问学段，讲法按学段调整：

- 学龄前：游戏、故事、选择、匹配。
- 小学：具体例子 → 分步示范 → 相似练习。
- 中学：条件分析 → 方法和依据 → 错因和变式。
- 大学：原理、推导、案例。
- 在职：先看能做出什么，再看最小步骤。

**验证范围**：代码本身不限学科。评测阶段建议先在少数几个学科的基础概念上做深，再扩展。

## 二、核心机制

每个机制按同一个模板写：**证据 → 机制 → 现在怎么实现 → 还差什么 → 怎么评测**。机制一、二是产品亮点，机制三、四是支撑能力，机制五是亮点的使用边界。

### 机制一：模糊地带探测 ★

**证据**：解释深度错觉（Rozenblit & Keil, 2002）；学生普遍过度自信（Hacker et al., 2013）；测试本身就是学习（Karpicke & Roediger, 2007）；掌握程度可以从作答记录推断，不需要学习者自己报告（Gervet et al., 2020）。

**机制**：不等学习者问出来，用两种方式主动探测：

- 讲完一块就出一道小题；一组练习由程序判分。
- 识别隐式信号，比如“这个我懂了，下一个吧”可能是半懂不懂，照样轻松地问一题，不预告“现在要考你”。

**现在怎么实现**

- ✅ 意图识别：每条消息归入 A–G 七类之一（概念、解题、练习、规划、闲聊情绪、越界、不明确），并标记是否为隐式意图。
- ✅ 讲完一块就出一道检查题：主 agent 讲完后声明“要检查这一块”，出题 agent 根据这一轮的讲解出一道单选题，接在回复后面，由程序判分并计入掌握程度。学习者说“懂了”也照样出；学习者明确不想做就不出。
- ✅ 程序判分的练习：一次只出一题；答案只保存在程序里，回复里看不到；不会重复出题；答完、讲完错因才出下一题；选项会变成可点击的按钮。
- ✅ 学习者可以说“换一题”：这题不计分，程序直接换一道。
- ✅ 掌握程度由程序计算（0 到 1 的分数，答对按难度加分，答错扣分），模型不能自己评分。陪伴者代答不计入。
- ○ 按掌握程度和复习时间主动安排复习，比如下次开场先考一道到期的题。

**评测**：被探测出的“模糊知识点”与人工标注的一致率；追问后学习者真的展开学习的比例。

### 机制二：错误归因与利用 ★

**证据**：错误管理训练元分析（Keith & Frese, 2008）；它的作用来自情绪调节和反思（Keith & Frese, 2005）；先尝试再讲解（Kapur, 2014）；智能辅导系统几十年研究的一条核心结论是：诊断和修复深层误解，是接近真人辅导效果的关键（D'Mello & Graesser, 2023）。

**机制**：答错时不轻易归为“粗心”放过，而是找到原因，针对原因换一种讲法。让学习者完整经历“犯错 → 找原因 → 针对性重学”。

**现在怎么实现**

- ✅ 答错的那一轮只给反馈和讲解，不急着出下一题。
- ✅ 主 agent 在本次对话要点里记“卡在哪”：必须逐字引用学习者原话，程序会核对原话是否真的说过。

✅ **错因分四类**：

| 错因 | 意思 | 例子 |
|---|---|---|
| 概念性误解 | 对概念本身理解错了 | 认为分母越大，分数越大 |
| 步骤性跳跃 | 知道方法，但漏了步骤或顺序错了 | 通分时只改分母不改分子 |
| 审题偏差 | 会做，但看错或漏看了题目条件 | 题目问“剩下的”，却算了“拿走的” |
| 迁移失败 | 熟悉的情境会，换个情境就不会用 | 会算披萨的几分之几，换成“一小时的几分之几”就不会 |

“审题偏差”必须说出读错了哪个条件，不能笼统地归为“粗心”。

- ✅ **疑似错因**：出题 agent 出题时，就给每个错误选项标好“选它说明可能是哪种误解”。学习者选错，程序马上知道疑似原因，主 agent 据此追问“你是不是觉得……？”。
- ✅ **确认错因**：学习者自己说出了思路、并且和疑似原因一致，才算确认。整理笔记时，确认过的易错点写明错因类型，没确认的记为“原因待确认”。
- ✅ **反复出错就换讲法**：同一个知识点、同一类疑似错因在本次对话里出现第二次时，程序标记“反复出错”，主 agent 必须换一种讲法或回到前置知识。
- ✅ **连续同类答错额外扣分**：掌握程度另按学习记录计算。这个知识点上一次判分也是同一类错因答错时，这次额外扣 0.1。它看的是学习记录里的上一次作答，可以跨对话；中间答对过一次就不叠加。所以“换讲法”和“额外扣分”的触发条件不完全相同。

**评测**：同类错误的复发率（下降说明归因有效）；归因结果与人工标注的一致率。

### 机制三：主动加工与多模态讲解

**证据**：投入越主动，学习效果越好（Chi & Wylie, 2014）；多媒体学习理论（Mayer, 2002；Mayer & Moreno, 2002）。

**机制**：讲解不止于文字。生成可以操作的图，让学习者自己拖动、逐帧观察，把学习从“看”变成“动手”。

**现在怎么实现**

- ✅ 七种图：对比表、步骤流程、记忆卡、一次函数互动图、分步图解（逐帧）、结构图、AI 配图。
- ✅ 讲原理、讲过程时，用可以检查的分步图解；只有学习目标是“看外观”时才用 AI 配图（FLUX.2-pro）。AI 配图不当作原理的证据。
- ✅ 质量流程：画图 agent 生成 → 程序在本地试渲染 → 另一个 agent 独立审阅（是否符合需求、事实是否一致、标签是否清楚、互动是否有用、是否会误导）→ 不通过最多重画一次 → 还不行就如实说明这次没生成。
- ✅ 可以看图出题：题目依赖讲解时的图时，程序等图生成完再出题。
- ✅ 出题也可以配图：考外观识别、情境判断，或学龄前、低年级看图比读字容易时，出题 agent 可以请求一张 AI 配图。答案依赖精确数量、数字、文字、尺寸或原理细节的题不用 AI 配图（AI 配图数不准、写不了字）。配图生成失败时，程序请出题 agent 改出一道纯文字题。
- ✅ 图里的事实如果依赖检索资料，只有资料完全核实后才画。
- ○ 记录图的打开率和互动时长。

**评测**：互动图打开率和互动时长；同一知识点有图、无图两组的记忆保持率对比。

### 机制四：结构化沉淀

**证据**：做笔记的元分析效应（Kobayashi, 2005, 2006）；概念图促进有意义的学习（Wang et al., 2025；Han, 2025）；做笔记、画概念图、自我解释都是被验证过的有效活动（Chi & Wylie, 2014）。

**机制**：把学到的东西整理成结构化笔记，而不是聊天记录摘要。内容包括：知识点（带前置知识和相关知识点，构成知识图谱的边）、易错点和错因、复习安排、学习者画像。这份笔记有两个用途：给学习者复习，也是 agent 下次对话的依据。

**v3 的调整**：整理时机从 v2 的“对话结束时自动整理”改为“练完一组题后问一句，同意才整理；也可以随时说‘整理笔记’”。原因有三个：

1. 笔记是学习记录，存不存应由学习者决定。
2. 网页上的对话没有明确的“结束”信号，关掉页面不会通知服务器。
3. 练完一组题，正好是一个自然的小结点。

**现在怎么实现**

- ✅ 练完一组题后询问是否整理；同意后，笔记 agent 根据这次对话里学习者说过的话整理。
- ✅ 每条笔记的依据必须逐字出现在学习者说过的话里，有一条对不上整份都不存。教练的回复和对话要点都不能当依据。
- ✅ 判分和掌握程度每轮由程序保存，不依赖整理笔记。
- ✅ 页面上的“我的笔记”面板可以直接查看：关于我、学过的知识点和掌握情况、容易错的地方、复习安排。
- ◐ 知识图谱：每个知识点记录前置知识和相关知识点（图谱的边），已经保存，但还没有展示。
- ○ 知识图谱的可视化展示。
- ○ 复习时间结构化（现在只记文字，比如“下周三”），用于到期提醒。

**评测**：笔记对本次知识点的覆盖率；前置、相关关系的准确率；第二次对话里是否正确用上了笔记。

### 机制五：学习意愿边界（“不想学”路线）

**为什么要有**：一个会主动探测的学习 agent，最大的产品风险不是探测不到，而是什么时候都在探测。学习者没有学习意愿时还出题追问，亮点就变成了打扰。所以探测只在学习者想学时启用。

**现在怎么实现**

- ✅ 识别为闲聊或情绪（E 类）时，不调用任何工具，不出题，不追问“你真的懂了吗”。
- ✅ 先回应感受，不说教，不制造愧疚；孩子不想玩就允许结束。
- ✅ 不记录情绪。v2 写的是“情绪状态写入记忆”，本版删掉：情绪属于敏感信息，记下来也容易让下次对话带着成见。
- ◐ 冷知识、看图猜现象这类轻互动，现在靠提示词引导，没有专门的流程。
- ○ 开了学习记录时，记下学习者感兴趣的主题，下次可以从这里轻轻开场。

## 三、用户流程

### 3.1 第一次见面

1. **打招呼**：一两句话说明“我是学习教练，可以讲概念、陪你解题、出小题看看是不是真学会了，需要时还能画图”。如果学习者第一句就带着问题，先记下，问完再讲。
2. **三个选择题**（可以直接点按钮，也可以回复“跳过”）：
   - 这次是谁在学？我自己 / 我是家长或老师，帮孩子用
   - 现在在哪个阶段？学龄前、小学、初中、高中、大学、已工作、不想说
   - 要保存学习进度吗？只记学习情况，不记个人信息，随时可以关掉或删除
3. **可能未满 14 岁**（学龄前、小学、初中或不想说）：保存学习记录需要家长确认；家长不在就先不保存，照常学习。
   - ◐ 目前只有开场选了“我自己”和上述学段时才会拦。开场选“跳过”（学段未知）、回访的学习者或演示模式下说“开启记录”，会直接开启，不再请家长确认。学段未知时也按“可能未满 14 岁”处理，列入待开发。
4. **回答一开始的问题**，进入学习主线。

这些问答完全由程序完成，不调用模型。回访的学习者不再重复自我介绍。演示时可以打开演示模式，跳过这些问题。

### 3.2 学习主线

1. 学习者说想学什么，比如“光合作用”。
2. 主 agent 判断要不要检索、要不要画图、要不要出题。稳定的基础知识不检索；有时效性或拿不准的事实才检索和查证。
3. 分块讲解，每讲完一块，出题 agent 出一道检查题，由程序判分。需要时配互动图或 AI 配图。
4. 学习者想练习，或同意检查时，进入程序判分的练习，默认 3 题、一次一题。
5. 答错：先给反馈，找原因，换一种讲法，再继续。
6. 一组题做完：如果开着学习记录，问一句“要把这次学的整理成笔记吗？”
7. 下次再来：主 agent 读得到学习笔记，知道哪里薄弱。（按复习时间主动开场考一道题还在计划中。）

### 3.3 “不想学”路线

学习者说累了、不想学，或者回复很敷衍时：

1. 接纳状态，不劝学。
2. 可以提供轻互动，比如一个冷知识、看图猜现象，不预告“这是学习”。
3. 不出题，不追问。
4. 留门收尾：“想聊的时候随时来。”
5. 学习中途出现挫败时，同样可以转到这条路线。

### 3.4 学习记录由学习者控制

| 学习者说 | 结果 |
|---|---|
| “开启记录” | 开始保存学习进度。开场选过“我自己”和可能未满 14 岁的学段、且没有家长确认时，会先请家长确认（学段未知时还不会拦，见 3.1） |
| “关闭记录” | 不再保存，也不再读取 |
| “删除记录” | 先提醒删除后找不回来，回复“确定删除”才删 |
| “整理笔记” | 随时把这次对话整理成笔记 |

对话记录只保存在学习者自己的浏览器里，不上传服务器，可以在“历史对话”里翻看，也可以一键删除。

### 3.5 页面结构（演示网页）

- 标题和简介
- “需要邀请链接”提示：链接里没有正确邀请码时显示
- 主区域：有正确邀请码时显示
  - 对话框：配图直接显示在对话里
  - 互动图面板
  - 选项按钮：回复带编号选项时出现，点击即发送
  - 输入框和发送按钮
  - 新会话；清空演示数据（只在演示模式出现）
  - 我的笔记（折叠）
  - 历史对话（折叠）：最近 20 次，只读，可删除

## 四、技术结构

### 4.1 Multi-agent 结构

```text
                                  学习者
                                    │ 一条消息
                                    ▼
               ┌────────────────────────────────────────┐
               │                主 agent                │
               │    判断意图、写搜索词、派活、写回复    │
               └────────────────────┬───────────────────┘
                                    │ 派活：没有依赖的子 agent 同时开工
         ┌─────────────────┬────────┴────────┬─────────────────┐
         ▼                 ▼                 ▼                 ▼
  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
  │  核对 agent  │  │  画图 agent  │  │  出题 agent  │  │  笔记 agent  │
  │  查证、审图  │  │  设计教学图  │  │ 出题、标错因 │  │   整理笔记   │
  └──────────────┘  └──────────────┘  └──────────────┘  └──────────────┘

           每个子 agent 只做一件事，把结构化结果交回主 agent；
                        子 agent 之间不直接通信。
```

- **主 agent 是中心**，也是唯一面向学习者说话的角色。每一轮它先判断要做什么：能直接回答就直接回答；需要帮手时，决定派哪几个子 agent、谁要等谁；要查资料时，它自己写好 2–4 条搜索词交给程序去搜。最终回复由它来写。

**四个子 agent 各管一件事**：

| 子 agent | 负责 | 什么时候派 |
|---|---|---|
| 核对 agent | 从搜到的资料里提取说法，逐字引用来源；另外负责独立审阅画好的图 | 每次搜到资料之后；每张图发布之前 |
| 画图 agent | 选图的类型，设计教学图 | 学习者要图，或图对理解有明确帮助时 |
| 出题 agent | 出一道单选题；给每个错误选项标上疑似错因；需要时请求题目配图 | 讲完一块之后；学习者要练习时 |
| 笔记 agent | 把学习者这次说过的话整理成结构化笔记 | 练完一组题、学习者同意整理时（或学习者说“整理笔记”） |

- **子 agent 之间不直接通信**：每个子 agent 只拿到完成自己这件事需要的内容，做完把结构化结果交回主 agent，由主 agent 汇总成回复。
- **派活由一层调度程序执行**：主 agent 给出计划后，调度程序按计划同时启动子 agent，检查每个结果是否合格，等齐后交回主 agent。这层程序不替主 agent 做判断，只负责执行和检查（见 4.5）。
- **用到的外部服务**：检索走维基百科或 Tavily；AI 配图走 FLUX.2-pro；学习笔记存在 SQLite。
- **两个入口共用同一套结构**：Foundry 托管接口（`main.py`）和演示网页（`space/app.py`）。

### 4.2 并行调度

以“练习中讲一个需要查证的知识点，配一张图，再出一道题”为例：

```text
主 agent 判断：这轮要查资料、画图、出一道练习题，并写好搜索词
   │
   ├──> 程序搜索 ──> 核对 agent（查证） ─────────┐
   ├──> 画图 agent ──> 核对 agent（审图） ───────┤
   └──> 出题 agent（需要时配图） ────────────────┘
                                                 │
                                                 ▼
                                          主 agent 写回复
```

- **三条线同时开工**。每条线内部有先后：程序用主 agent 写的搜索词搜到资料 → 核对 agent 查证；画图 agent 出图 → 程序本地试渲染 → 核对 agent 审阅。
- **核对 agent 可以同时出现在两条线上**：每次调用都是独立的，互不影响。

**谁等谁由主 agent 声明内容依赖，程序推导先后**：

| 主 agent 的声明 | 程序怎么排 |
|---|---|
| 图里的事实要用这轮的检索结果 | 画图等“检索 → 核对”完成后再开始 |
| 题目考的是这轮检索到的内容 | 出题等“检索 → 核对”完成后再开始 |
| 题目要看图才能答 | 出题等图审阅通过后再开始 |
| 没有声明 | 图和题默认等检索（检索只在拿不准的事实上才会发起）；题默认不等图 |

依赖只会从检索指向画图、从画图指向出题，不会互相等待而卡住。

- **笔记 agent 不在教学的这一轮里派出**：这一轮主 agent 只标记“哪些话值得记”；练完一组题、学习者同意整理时，再单独派出笔记 agent。这样教学的每一轮不会因为整理笔记而变慢，笔记也只在学习者同意时才整理。
- **讲完一块后的检查题在回复写好之后出**：出题 agent 要根据这一轮实际讲的内容出题，所以等主 agent 写完回复再派出，题目接在回复后面。
- **判分不需要派 agent**：学习者选了选项，程序在派活之前就直接判出对错，不占用这几条线的时间。
- **每轮最多 12 次模型调用**，并且为最后写回复预留名额；某条线失败只影响它自己，回复里如实说明。

### 4.3 各 agent 收到什么、交出什么

| 角色 | 做什么 | 收到什么 | 交出什么 |
|---|---|---|---|
| 主 agent：判断 | 识别意图，选择直接回答或派哪些子 agent，声明内容依赖，要查资料时写搜索词，更新对话要点 | 最近对话、对话要点、学习者背景卡、学习笔记切片、程序状态 | 直接回复，或一份计划（含检索问题和搜索词） |
| 主 agent：写回复 | 根据各子 agent 的结果写给学习者的回复 | 较短的最近对话、要点、计划、精简后的检索结果、题目（不含答案）、图的说明、各条线的执行情况 | 学习者看到的回复 |
| 核对 agent | ① 查证资料；② 审阅图 | ① 问题和来源摘录；② 需求、图的规格、渲染结果 | ① 说法和逐字引用；② 通过、要改或资料不够 |
| 画图 agent | 选图的类型，写出图的规格 | 画图需求、学习目标、背景卡、讲过什么、学习者的要求、最近对话 | 图的规格（不写网页代码） |
| 出题 agent | 出一道单选题，标出每个错误选项的疑似错因，需要时请求配图 | 主题、难度、题的用途（检查或练习）、这一轮的讲解（检查题）、出过的题、背景卡、讲过什么、卡在哪；按依赖带上核实过的资料或图 | 题目、选项、答案、解析、错因标注、配图请求。除题目和选项外都由程序保管，作答前谁也看不到 |
| 笔记 agent | 整理结构化笔记 | 学习者这次说过的话、标记过的轮次、要点、判分结果、背景卡、已有笔记切片 | 画像、知识点、易错点、复习安排 |

**模型**：核对（查证和审图）、画图两个角色用 gpt-6-luna（画复杂互动图时 mini 常常过不了审图），主 agent（含写搜索词）、出题、笔记用 gpt-5.4-mini，AI 配图用 FLUX.2-pro，都部署在 Azure AI Foundry。每个角色的模型由 `LEARNING_COACH_MODEL_<角色>` 配置，没配置的用默认部署 `AZURE_AI_MODEL_DEPLOYMENT_NAME`。

**为什么不单设检索 agent**：原来有一个检索 agent，只负责把问题拆成 2–4 个搜索词。这一步很小，主 agent 判断时本来就要写“查什么”，单独一个 agent 却要多一次模型调用，所以并进了主 agent。代价是搜索词改由 gpt-5.4-mini 写（原来用 gpt-6-luna），搜索质量要靠真实检索样本确认。

**为什么出题单独做一个 agent**：

- 出一道好的检查题是专门的手艺：每个错误选项都要对应一种常见误解，这些规则写在出题 agent 自己的指令里，比塞在主 agent 的大指令里更清楚。
- 错误选项标好疑似错因，判分时才能知道错在哪类，“反复出错就换讲法”的规则才能生效。
- 出题 agent 只带自己那份短指令，每次出题的输入少很多，调用次数不变。

**为什么查证单独交给核对 agent**：如果由写搜索词、写回复的主 agent 自己判断资料可不可靠，就只能依赖一个模型自觉。交给核对 agent 后，它必须逐字引用来源，程序再检查引用是否真的出现在摘录里。

### 4.4 一条消息进来之后

1. **程序先处理确定的事**，不调用模型：学习记录的开、关、删；第一次见面的问答；是否整理笔记的回答。
2. **组装上下文**：按 token 预算截取最近对话，加上对话要点、学习者背景卡和学习笔记切片（见 4.6）。
3. **主 agent 判断**，二选一：
   - 直接回答：一次模型调用；讲了新内容时再派出题 agent 出一道检查题，共两次。
   - 一份计划：要检索什么（连同 2–4 条搜索词）、画什么、是否出题，以及内容依赖（图是否用检索结果、题是否用检索结果、题是否要看图）。
4. **程序检查和兜底**：
   - 测验进行中、学习者给了明确选项时，一定进入判分，即使模型想直接回答。
   - 学习者明确要图，一定走画图流程；画不出来要说明。
   - 每个能力都要附上理由，理由必须逐字引用学习者这句话。
   - 闲聊、越界、不明确的意图不调用任何能力；没开学习记录不标记笔记证据。
5. **派出子 agent 并行工作**：互不依赖的同时做，有依赖的等前面完成（见 4.2）。判分由程序直接完成，不需要模型。
6. **主 agent 写回复。**
7. **校验后再保存**：回复通过格式和规则校验后，才发布图、保存判分记录；校验不通过，这一轮什么都不写。

### 4.5 模型提出，程序决定

| 事情 | 模型做什么 | 程序做什么 |
|---|---|---|
| 是否调用能力 | 提出计划和理由 | 检查理由是否逐字引用学习者原话，按规则拒绝不该调用的 |
| 执行顺序 | 声明内容依赖 | 推导先后和并行 |
| 判分和掌握程度 | 出题 agent 出题、标注疑似错因 | 检查每个错误选项都标了错因；保管答案；判对错；记录疑似错因；计算掌握程度 |
| 资料可信度 | 提取说法和引用 | 核对引用、判定可信等级（两个独立完整来源才算核实） |
| 链接 | 不能自己写 | 回复里的链接只能来自真实检索结果 |
| 笔记 | 整理内容 | 核对每条依据都是学习者原话；学习者同意才写入 |
| 学习记录开关 | 无 | 只认程序识别的明确回答 |

### 4.6 上下文管理

**原则**：每个 agent 只拿自己需要的内容，用量按 token 计算。完整对话保存在学习者的浏览器里，供学习者翻看；agent 依靠对话要点和学习笔记接上前文。

**主 agent 每轮看到的内容**

| 部分 | 上限 | 谁生成 |
|---|---|---|
| 指令和输出格式（固定不变，放在最前面，可被缓存） | 约 7000–9000 token（待实测确认） | 固定 |
| 学习者背景卡：学段、谁在学、记录开关、学习目标原话、任务情况、做题成绩 | 约 500 | 程序 |
| 学习笔记切片：和当前主题相关的知识点优先，其次是掌握最差的 | 1500 | 程序 |
| 对话要点：讲过什么、卡在哪、要求和纠正、还没回答的问题 | 1000 | 主 agent 提出，程序检查 |
| 最近对话：至少保留最近 3 轮完整；单条超过 1500 token 时只留开头和结尾 | 判断时 4000，回复时 2000 | 程序 |

**子 agent**：都拿到同一份简短背景卡（学段、学习目标、谁在作答），再加各自需要的部分。比如出题拿“讲过什么”和“卡在哪”，画图拿“讲过什么”和“学习者的要求”。

**检索结果瘦身**：主 agent 只拿到结论、可信等级和出处，不再拿每条最长 3000 字的网页原文。

**计数和记录**：发送前用 tiktoken 估算 token（加载失败就粗算）；每次调用后记录接口返回的实际用量和缓存命中量，按角色和阶段分开。所有上限都可以在配置里调整。

### 4.7 数据存在哪里

| 数据 | 存在哪里 | 谁写入 | 保存多久 |
|---|---|---|---|
| 程序状态：做题进度、任务、对话要点、开场问答结果 | 服务器内存 | 程序（要点由主 agent 提出、程序检查） | 本次对话 |
| 学习笔记：画像、知识点、易错点、复习安排 | 服务器 SQLite | 笔记 agent 整理、程序核对后写入；开场时学习者自己选的学段由程序写入 | 按学习者编号跨对话保存，直到学习者删除或服务器重启（见下文） |
| 掌握程度和判分记录 | 服务器 SQLite | 程序，每轮校验通过后写入 | 同上 |
| 语义记忆：笔记要点的短句 | Foundry Memory（设置了才开启） | 程序在笔记写入后同步，不含学习者原话 | 跨对话，不随服务器重启丢失；出错时退回只用 SQLite |
| 完整对话记录、匿名学习者编号 | 学习者浏览器（加密） | 网页 | 直到学习者删除或清除浏览器数据 |

学习笔记、掌握程度和判分记录只在开启学习记录时写入。

跨对话保存靠学习者编号：演示网页传浏览器里的匿名编号；Foundry 托管接口传平台注入的用户编号（请求头 `x-agent-user-id`），取不到时只按会话保存；命令行只按会话保存。

托管容器和 Space 的数据目录都在 `/tmp`，服务器重启后 SQLite 会清空。开启 Foundry Memory 时，笔记要点的短句还在，但掌握程度和判分记录要长期保留，需要接持久磁盘（待开发第 7 条）。

和 v2 的区别：v2 写“笔记 agent 是记忆的唯一写入者”。现在掌握程度由程序根据判分直接计算和写入，不交给模型，所以不再是唯一写入者。每类数据仍然只有一个写入方。

### 4.8 可靠性与降级

- **格式校验**：输出不符合格式时，带着纠正提示重试一次。
- **网络或超时**：失败时重试一次，再失败就给出固定的兜底回复，这一轮不写入任何东西。
- **调用预算**：每轮最多 12 次模型调用，并为最后的回复预留名额。
- **时间上限**：单次调用 45 秒，画图整个流程 60 秒，整轮 180 秒。
- **局部降级**：检索、画图失败时，在回复里如实说明，不影响主对话。
- **不泄露**：日志只记角色、阶段、结果、耗时和 token 数，不记对话内容和服务商的报错原文。

### 4.9 代码分层

| 目录 | 职责 |
|---|---|
| `domain/` | 领域规则：数据协议、路由规则、开场问答、掌握程度、上下文组装。不调用模型，不读写数据库 |
| `service/` | 编排流程，以及它需要的接口定义 |
| `adapters/` | 外部能力的实现：模型调用、搜索、渲染、生图 |
| `db/` | 学习笔记和图的存储 |
| `api/` | 接入层：Foundry 托管接口 |
| `server.py` | 唯一的组装点：选择具体的模型、存储和搜索实现 |

接口由 `service/` 定义，`adapters/` 和 `db/` 去实现。换生图模型、换搜索服务、换存储方式，只改 `server.py` 一处。分层规则由架构测试强制检查。

4. **配图的视觉核对**：题目配图现在没有经过看图检查，学习者觉得图不对可以“换一题”；之后可以让核对 agent 直接看图，确认图和题一致。
5. **学段未知时的家长确认**：开场跳过、回访或演示模式下开启记录，也按“可能未满 14 岁”请家长确认。
6. **学习记录持久保存**：给托管容器和 Space 的数据目录接持久磁盘，重启后掌握程度和判分记录不丢。
7. **工程小修**：给 `agent-framework-foundry-hosting` 加版本上限（新版会让 2 个测试失败，目前靠锁文件部署不受影响）。
